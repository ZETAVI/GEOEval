# 入口与首次归属设计

Status: Approved direction; A0 locally verified; integration pending under #100. 用户确认整体构思与固定 30 天期限，运行结果以验证证据为准。

## 1. 业务场景与边界

| 动作 | 已确认结果或候选处理 |
| --- | --- |
| 从 A 链接进入，再访问根目录主页 | 保留 A；首页注册按钮与首次入口地址相同 |
| 来源有效时刷新、关闭后重新打开同一浏览器 | 保留来源和入口；普通访问不延长首次代理来源期限 |
| 只浏览官网，再首次打开 A 链接 | 公共访问上下文升级为 A 来源，尚未建立账号归属 |
| 同一有效访问上下文先 A 后 B | 保留首次有效代理商 A，不凭后续链接抢占 |
| 从首页复制 A 入口给另一个未注册访客 | 对方获得同一个获客入口，不获得原访客身份/资料；按对方自己的来源上下文决定首次归属 |
| 从首页复制普通入口 | 不携带任何个人信息，也不覆盖接收者已有有效代理来源 |
| 已有客户账号打开任意入口 | 登录，不修改账号归属 |
| 来源凭据缺失或清除后直接访问根目录 | 没有证据时按普通访客处理；再次打开有效代理链接可以重新识别，不用指纹或 IP 猜测 |
| 入口无效、停用或代理账号失去资格 | 已有其他有效来源则保留；没有有效来源时显示中性入口不可用提示，不静默建立错误代理关系。首片采用此有界失败处理，不改已有账号 |

用户已确认来源期限：首次有效代理访问起固定 30 天，普通浏览不续期。期限后的新有效邀请可以开启新来源周期。注册后关系独立持久存在，不能被 Cookie 到期清除。

## 2. 拥有的数据及其生命周期

- **EntryLink**：同格式、不可猜测的公开入口标识，指向公共来源或一个代理商。它可以分享，不是登录密钥；可用性由 Agency 与 Identity 的当前账号资格共同决定。入口不含手机号、代理商 ID 或其他个人资料。
- **EntryVisit**：浏览器持有随机访问凭据，服务端存其摘要和上下文；记录当前公开入口、首次有效代理来源及期限。公共来源可升级一次为代理来源；同一有效上下文用行锁竞争第一次有效写入，不按网页上的时间戳决定输赢。
- **ChallengeAttribution**：验证码流程的来源快照，由 Agency 持有并与 Identity 的 challenge ID 对应。开始一次新的验证码流程时冻结可信来源，后续页面导航不改写；验证码重发/替代遵循 Identity 现有生命周期。原 challenge 有效期间不因普通来源期限到达而换人；代理失去资格仍在完成事务内复核。
- **CustomerAttribution**：客户账号唯一的当前归属，初始可为空；首次绑定保存来源证据与审计。客户品牌、报告、余额仍留在原 owner。后续管理员迁移只修改此关系和追加历史，不重建客户数据。

公开入口标识需要被首页精确复用，可以作为公开定位符保存；访问凭据与会话凭据分别生成，不能把可分享的入口 key 当作个人凭据。匿名记录按有限批次到期清理；已被注册审计引用的最小来源事实不得随匿名清理丢失。

## 3. Web 与 API 的衔接

当前 Web 为 Next 16.3.2，Identity 位于独立 Nest API；现有登录 Cookie 属于 API 所在 host。不能为了获客而扩大其 Domain，也不能假设 Web/不同 API host 自动共享 host-only Cookie。

入口 Route Handler 位于 Web 同源：处理公开入口、保存 Web host 的 HttpOnly/Secure 访问 Cookie，再进入现有注册页面。当前路径 `/e/<opaque>` 是分享/首页按钮地址，注册展示继续复用 `/enter`；路径名属于可逆实现细节。

主页已有访问凭据时读取其有效入口，并输出同一 href；无凭据时使用同格式的公共入口。入口解析失败不能先显示错误公共链接再补成代理链接。所有包含入口上下文的 HTML、接口及重定向显式避免共享缓存，前端路由缓存/返回缓存也须覆盖实测。框架 prefetch 不得抢先改变来源，入口选择以真实导航为边界。

为把 Web host 的访问凭据交给验证码 owner，只增加同源的窄“获取验证码”桥接：服务器读取获客 Cookie，向固定后端传递手机号和凭据；后端校验凭据并冻结来源。桥接不得接受任意目标 URL、转发全部 Cookie、成为开放代理或改变原登录会话签发。验证码完成仍走当前 Identity API 和原有登录 Cookie。新注册后按原品牌引导继续，不增加客户选择项。

来源失效时提供仅供已有账号登录的兜底入口。限制由 Identity 冻结到验证码记录，完成时拒绝创建新账号；既有账号继续原登录，不读取失效来源改绑。该状态不能由完成请求覆盖。

HttpOnly 不是对浏览器使用者隐藏的保证；链接格式和连续使用体验一致，不承诺不同设备或主动清除上下文后仍无法区分入口。业务鉴权不能依赖“看不懂 key”。

## 4. 模块与事务

Agency 只承担入口/归属，不成为第二个身份服务。Identity 保留验证码验证、账号唯一性、登录和会话；Web 不拥有归属判断。

已落地的窄接口为：入口解析/恢复、向 challenge 固定来源、向新账号提交初始归属。业务调用不接收任意 agentId；数据库事务类型只出现在 owner 的基础设施适配器。沿用现有 owner-bound `bind(tx)` 模式，不引入事务框架。

**重要接缝：** 变更前 `completeChallenge` 采用按手机号 upsert，无法直接以返回账号判断“这次是否新建”。实现用 createMany 的冲突跳过结果在同一事务中确定是否新建，不能用 createdAt 相等或事先 find 的结果猜测。只有这次真正创建的终端账号才调用首次归属写入；旧账号不进入此路径。

验证码消费、账号创建、来源快照核验、关系与审计、会话创建必须原子提交。关系写入失败整笔回滚，不能先让用户注册成功再靠后台补绑。响应丢失后重新获取验证码登录已有账号，不得把这次重试当成新绑定。

并发设计锁定并消费 challenge 后，通过 insert-on-conflict 的创建结果区分新旧账号，再锁客户账号。仅当本事务刚创建客户时，才读取并共享锁定代理资格与入口，最后写归属；新客户在提交前不可能被另一事务读取，既有账号不进入归属资格锁路径。管理员入口操作先按 ID 顺序锁定管理员/代理事实，之后锁入口；不反向锁客户或 challenge。代理停用/改角色与注册完成必须由相同事务内的 Identity-owned 资格读取判定；实施前验证其与现有管理员治理锁顺序兼容。

模块装配不采用 Identity↔Agency 的双向 `forwardRef`。采用 Identity 自有的无服务装配依赖的同事务账号事实适配器；Agency 的无状态注册事务适配器调用该叶子接口，IdentityRepository 调用 Agency 的注册适配器。两者不导入对方的 Nest 主模块。Agency 业务核心不依赖 AuthenticationService；根 API 装配只连接各 owner，不构建通用权限引擎。装配由固定代码 review 核验；具体签名以 owner 代码为准。

### 后续购买一致性

当前 Commerce 购买已经钱包先锁、原请求幂等恢复、订单/扣点/Delivery 同事务写入。未来订单必须从同一一致性边界冻结代理商和佣金率，管理员迁移须与之序列化；不能在订单提交后异步查询当前归属。此能力不在本入口首片实现范围，**真实代理获客激活必须等该接缝就绪**。旧订单没有快照时明确为历史未采集，不从现在的代理关系倒推。

## 5. 故障与恢复

| 可达故障 | 处理与最小证据 |
| --- | --- |
| 回主页把 A 换成公共 | 同一上下文只读恢复；浏览器比较原入口和首页 href |
| 同一有效上下文 A/B 并发写首次来源 | 行锁与条件更新；真实 PostgreSQL 并发验证一个赢家 |
| 初次无 Cookie 的两个独立访问同时建立上下文 | 浏览器此前没有共同身份；不得宣称跨独立上下文全局先到先得，具体首启协调需浏览器验证 |
| 多标签或改手机号使验证码来源串用 | 来源绑定 challenge，而不是完成时读取可变 Cookie；交叉 challenge 测试 |
| 注册关系写入失败 | 账号/验证码消费/关系/审计/会话同事务回滚；注入一次失败重试 |
| 注册成功但响应丢失 | 重新登录原账号，关系不重复或改绑；HTTP 故障验证 |
| 代理停用与注册竞争 | 同事务资格读取和治理锁；结果要么先合法完成，要么中性拒绝新归属，不留半成品 |
| API 暂时不可用 | 不清除有效来源，不降级成公共注册；有限重试，恢复后同源继续 |
| 共享缓存给另一访客 A 链接 | no-store 与两个浏览器上下文实测；不以组件测试代替 |
| 清理匿名记录 | 不删除注册归属/来源审计；到期与引用测试 |

## 6. 工具与来源

读取日期 2026-09-14。复用现有 Node 随机数、PostgreSQL、Next/Nest 和 API client；不新增第三方归因平台或全局依赖。Context7 CLI 不在当前环境中，本轮直接读取官方文档，没有为文档调研安装全局包。

- [Next cookies](https://nextjs.org/docs/app/api-reference/functions/cookies)：Server Component 可读 Cookie，写入应由 Route Handler/Server Function 完成。当前文档标注 16.3.5，本项目锁定 16.3.2，须以项目版本实测 Cookie/缓存行为，未升级依赖。
- [Next Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)：用于同源窄桥接和响应 Cookie；不假设运行时的默认缓存设置满足这里的隔离要求。
- [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)：host-only、HttpOnly、Secure 和跨源凭据边界。访问上下文失效由服务端判定，浏览器 Cookie 生命周期不是关系真相。
- [Nest modules](https://docs.nestjs.com/modules)：显式 imports/exports 界定 provider 可见性；本片避免双向模块依赖。
- [PostgreSQL locks](https://www.postgresql.org/docs/current/explicit-locking.html)：锁排序与死锁边界；文档不能代替本项目真实并发验证。

## 7. 迁移、回退和验收

A0 使用增量表/约束及默认 false 的验证码 existing_account_only 列，不重写既有账号、品牌或订单；旧账号初始无代理关系。当前手机号唯一约束继续生效。匿名路径有长度/数量/期限边界，不允许无界新记录重试；具体清理和速率沿现有入口策略定值后验证。

默认保持未激活；回退停新入口与新归属，保留已有账号关系、审计和后续订单义务，不能删表或退回会误认已归属账号的版本。启动实际代理客户前固定所有实例版本与开关，防止新旧注册进程混跑漏绑。

验收按 [tasks](tasks.md) 执行。当前 A0 的本地数据库、HTTP、生产构建产物和浏览器证据见 [verification](verification.md)；不代表生产或真实资金通过。

## 8. 架构审查结论

当前结论：**A0 implementation locally verified; ready for PR review**。用户认可整体方案并确定 30 天；本轮执行入口/注册有界切片，真实获客仍关闭，购买快照、佣金及迁移界面不扩入。

- 已消除的设计问题：主页重置公共来源；把公开链接当个人凭据；注册后异步补绑；读取 Web 无法获得的 API host Cookie；源码中没有创建结果却猜测新账号。
- A0 落实：固定 30 天；无效入口中性拒绝；同事务读取代理资格；只由管理员生成已有代理账号的入口，代理商只读自己的入口；默认关闭及禁止生产启用。
- 不要求新的通用事务框架、权限引擎、营销归因服务、缓存中间层或独立部署。本次固定 diff 已核对上述装配与事务接缝，验证范围见 verification。
