# 架构与恢复设计

## 目标与职责

Support 拥有工单、客户对话、普通工单领取和处理进度。Delivery 拥有履约、当前运营、约定退点总额及订单售后资格。Commerce 拥有钱包、原消费、一次实际退点和最终结算凭据。Recharge 拥有付款核验及到账恢复。应用层负责跨 owner 的短事务组合，不让各模块直接写对方私有表。

订单工单根据订单当前运营确定处理权，不复制负责人。普通/充值工单没有订单责任可继承，保有一个可领取的责任人。管理员按权限查询全部记录。代理的历史佣金资格不授予工单内容访问。订单无人领取时仍走原订单池；改派后后续处理权随之更新，旧操作人保留在历史中。

## 最小记录与公开操作

- Support 只需工单记录和追加对话/操作记录。客户状态为处理中、已处理；普通工单是否待领取由责任人为空表达，不增加客户状态。
- 工单关联发布订单、充值单或一般诉求。只有通过业务 owner 校验的引用可以打开业务详情。手填充值 ID 不匹配时返回不泄露他人信息的结果，不凭编号认定付款成功。
- Delivery 继续保存一份当前约定退点总额及修改审计，不建独立协商方案。修改 100 为 150 表示新总额 150，不是追加 150。实际结算后不能再修改已执行金额。
- 正常完成补首次完成时间，关闭复用首次关闭时间。任何发布结果修正、工单答复或实际退点都不能重置时间。
- Commerce 需要按订单唯一的最终结算凭据：即使退点总额为零，也能证明该单资金处理已结束，不制造零额 PointChange。正额凭据引用真实退点流水，保留最终金额和采用的协商版本。
- 创建/回复/领取/处理工单使用请求标识恢复原结果。系统结算保留自己的执行身份，同时引用运营确认记录；不得创建虚假运营账号或伪装人工点击。

公开业务接口保持窄：创建/读取/回复工单，领取普通工单，处理问题并更新订单约定，读取业务引用，执行一个订单最终结算。现有订单直接处理和工单处理组合调用同一条订单命令，无客户工单也能主动处理订单异常。

## 业务时序

1. 在途问题可多轮协商；同一处理中工单补充原记录。运营调整订单约定总额，客户始终看到同一待退文案。
2. 全部发布完成或终止剩余发布后，固定首次结束时间。正额终止也必须能够先结束发布，不等实际退点，解除现有关闭/退点的循环依赖。
3. 首次结束后的连续 72 小时内最多受理一次新的客户售后申诉。成功受理消耗机会，重复恢复不消耗，处理结束不恢复次数。员工主动沟通不冒充客户申诉。已经受理的在途/售后工单跨期继续处理。
4. 工单处理完成意味着本轮协商已确认，不表示约定退点已经到账；仍有待跟进的问题保持处理中。普通咨询/充值工单不作为全账户的佣金或发布订单结算阻断条件。
5. 时间届满、相关有效工单均已处理、最终金额确定后，系统完成一次结算。正额实际退点与凭据同事务成功，零额只写结算凭据。
6. 后续佣金仅消费最终结算凭据与原单快照；失败、未执行或仅有预计金额不能作为实际退点/佣金入账证据。

## 时间与并发

订单受理、预计金额变更、工单结束和最终结算在同一订单锚点上协调。工作人员身份按现有 Identity 窄接口校验，当前责任在锁内复核。客户钱包只在实际资金事务中获取，其他工单操作不持有钱包锁。

沿用现有顺序：需要身份校验时先 Identity，再钱包（仅资金操作），再 Delivery 订单，再关联工单/结算记录。不得出现工单先锁自身、再反向等待订单/钱包的写入路径。普通工单只锁当前责任与自身记录，不把全站工单串行化。数据库唯一性保护一次客户售后受理、一次结算和一次原单退点。

窗口判断使用订单锁取得后的数据库实际时间，不能使用浏览器点击时间或事务开始时间冒充受理时间。截止前成功受理才占用名额并阻止结算；截止时及以后不新增订单售后资格，已受理事项继续处理。窗口内已受理请求与结算不可能同时遗漏彼此。

同一事务中实际退点失败，结算凭据不能标记完成；重复投递恢复原结算，不再次改积分。积分来源和容量继续复用 Commerce，包括已有充值预留容量，不能为退点静默释放 Recharge 预留。

## 后台执行与恢复

复用项目已有 Worker 宿主和数据库持久状态，增加 owner-local 的订单结算执行入口；不把金额/资格判断放进 Redis 延时消息。唤醒只表示可以检查，最终条件必须重新从数据库取得。

现有 ProductWorkProcessor 主要编排 Evaluation，RechargeWorkerRuntime 属于充值；不直接塞进这两个业务协调器。允许在现有进程中注册小型结算运行器，按持久到期/重试记录有界扫描并调用 Commerce/Delivery/Support 的事务接口。数据库是唯一执行事实，即使唤醒丢失或进程重启也可重新发现。

到期但尚未处理完的订单不能堵住后续候选；调度需有界、避免重入，并在工单完成后再次检查。暂时性失败延后重试；记录不完整、历史资格无法证明等情况保留义务并进入内部核查，不制造客户到账成功。关闭进程停止接新批次并等待当前短事务退出，不涉及外部支付调用。

## 页面与关联

统一联系客服入口；订单详情可以带入订单，充值不增加专门入口，只提供可复制充值 ID，由客户粘贴到统一表单。列表摘要、详情互链。每次跳转都重验权限，不能把外键或 URL 当授权。

客户对话只保留一套。运营主动发现需要客户知晓/协商的问题时可以建单或补充已有单，并电话沟通后回写结果；内部技术重试不全部变为客户工单。不接入真实电话服务。

管理员综合视图读取各 owner 的积分、发布订单、充值、工单事实，积分与人民币分别展示。支付未付款结论必须来自 Recharge，不以本地超时或离开支付页判断。积分流水只有实际增减，不混入未付款订单。

支付线另已同步后续统一采用可见积分单位“⚡”、人民币用于支付和佣金、无障碍仍读“积分”。这是后续共同前端优化边界，本片不抢先修改公共充值页面或引入第二种账务单位；本轮客户待退文案语义保持用户原句。

## 迁移与退出

先在 OrbStack 专属任务库验证。追加工单、首次完成时间和结算凭据；保留原积分流水、退点唯一性和历史审计。修改正额关闭需要先到账等旧约束时，必须同时验证新旧有效数据，不删掉原来源和额度保护。

新订单采用新自动政策。已有实际退点的订单不得重新退点；已有正额待退约定保留金额/原因与内部处理入口。历史结束时间必须从可验证事实恢复，不能用部署时间重置；无法验证的存量不自动发钱，进入一次受控迁移核对。生产启用与真实存量迁移仍是单独运行边界，本片受控验收不授权执行它们。

回滚保留新表、凭据和原流水，先停自动结算接入，再回退兼容应用；旧手动入口不得重新执行已经自动结算的订单。不得以删表或删流水实现回滚。

## 架构审查结论

设计方向 ready for implementation under the approved controlled boundary。有真实跨业务受理需求，因此 Support 独立；履约/钱包不复制。未引入新外部服务、通用方案实体、复杂派单或审批。关键风险有对应验收，源依据见 source-brief.md。尚无运行证明，不能据此宣称已实现或生产可用。
