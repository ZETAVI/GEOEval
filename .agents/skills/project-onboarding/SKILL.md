# Project Onboarding

Teach only the context needed to contribute safely to one mission.

## Workflow

1. Define the mission as one Issue, review, release, or owned capability. State
   observable success and authority boundaries.
2. Build the reading path in this order:
   - nearest AGENTS and project routing;
   - relevant product language and current specs;
   - Issue, active change, and accepted decisions;
   - exact checkout, branch, revision, and relevant code;
   - existing tests, evidence, and known limitations;
   - handoff only when interrupted state cannot be recovered otherwise.
3. Explain the owner, lifecycle, public interface, failure modes, and verification
   seam with one representative scenario.
4. Ask the contributor to restate the goal, non-goals, current phase, and next
   safe action. Correct misunderstandings before work begins.
5. Return a compact context packet and source links. Do not create a permanent
   course or copy project documentation for one task.

For sustained team learning, record only proven reusable misconceptions or
knowledge gaps in the owning documentation or Skill; ordinary onboarding stays
ephemeral.
